Le fil rouge — de la demande à la production

Qualifier les usages

Répondre, rechercher, générer, agir via des outils ou exécuter un processus multi-étapes : chaque classe demande un pattern différent.

Définir la frontière de confiance

Classer les données, les utilisateurs, les clients, les régions, les droits et les règles de transfert. Cela élimine les architectures incompatibles avant le choix du GPU.

Choisir l’hébergement

Modèles, RAG, logs et outils peuvent résider à des endroits distincts. Une architecture hybride conserve la maîtrise du contexte et du contrôle d’accès.

Concevoir RAG et harness

Le RAG récupère le contexte pertinent ; le harness sélectionne le modèle, orchestre les outils, contrôle les permissions et vérifie les résultats.

Mesurer puis optimiser

Évaluer qualité, latence, coûts, réussite de tâche et risques. Optimiser la chaîne avant d’ajouter des GPU.

      Étape 3 — Retrieval Augmented Generation

      Le RAG : une chaîne complète, pas une base vectorielle

      Le RAG récupère des passages pertinents depuis des sources maîtrisées, puis les injecte dans le contexte du modèle. La qualité dépend autant de l’ingestion, des métadonnées et des ACL que du modèle.

      Contrôle critique : les droits doivent être appliqués avant ou pendant la recherche. Un document interdit ne doit jamais entrer dans le contexte du modèle. Les ACL ne doivent pas être laissées au jugement du LLM.

      Choisir le pattern RAG selon le cas

      Votre choix : cliquez sur le pattern adapté à votre cas. Il est appliqué aux réglages avancés et repris dans le récapitulatif.

      Basic / Naive RAG

      FAQ et procédures simples. Embeddings, recherche vectorielle, quelques chunks et citations. Suffisant si le corpus est propre et les questions directes.

      Hybrid RAG

      Code, identifiants, références, docs techniques. BM25 + vecteurs, fusion, filtres de métadonnées et reranker. Bon choix par défaut pour corpus mixtes.

      Hierarchical / Parent-child

      Manuels, contrats et longs PDF. Indexer de petits passages précis, puis rattacher au chapitre ou document parent pour restituer le contexte.

      Graph RAG

      Relations et questions multi-hop. Extraire entités et relations pour parcourir dépendances, dossiers ou concepts. Plus cher à construire et maintenir.

      Agentic RAG

      Recherche complexe et itérative. Le contrôleur reformule, lance plusieurs recherches et vérifie les preuves. Limiter les tours, le coût et les critères d’arrêt.

      Structured / SQL RAG

      Chiffres, statuts, soldes, indicateurs. Appeler des API ou requêtes SQL paramétrées. Jamais de SQL libre avec les droits de la base confiés au modèle.

      Pipeline d’ingestion : des sources à l’index

      ParsingPréserver titres, tableaux, code, pages, cellules et structure.
      ChunkingDécouper par unité de sens, section ou symbole, pas uniquement à taille fixe.
      MetadataSource, version, tenant, ACL, date, type, niveau de confidentialité.
      Atelier de paramétrage avancé

      Configurer finement le RAG

      Ces réglages constituent un profil expérimental. Ils doivent être comparés sur un jeu de questions métier annoté, et non considérés comme des valeurs universelles. Chaque paramètre est accompagné d’une explication : son effet, les arbitrages et les cas où le modifier.

      Afficher les 24 réglages du RAG — valeurs reprises dans le récapitulatif
      À mesurer : Recall@K, MRR/nDCG, groundedness, exactitude des citations, taux d’abstention, p50/p95, coût par requête, fraîcheur et taux de fuite ACL. Tester aussi les questions sans réponse, les contradictions, les documents injectant des instructions et les suppressions.

      Pipeline de requête : question vers réponse

      Bonnes pratiques

      • Réécriture / expansion de requête si utile.
      • BM25 + recherche vectorielle + filtres.
      • Reranker, déduplication et budget de contexte.
      • Citations vérifiables et possibilité de s’abstenir.
      • Versionner les corpus et réindexer incrémentalement.

      Anti-patterns

      • Chunks arbitraires qui coupent les idées.
      • Vector search seule pour les symboles et références exactes.
      • Tout le document injecté à chaque question.
      • Confondre proximité sémantique et vérité.
      • Mettre le contrôle d’accès dans le prompt.

      Réglages de départ à benchmarker

      ParamètreDépart indicatifQuand ajuster

      RAG spécialisé par type de données

      Code source / Git

      Parser AST, indexer symboles, classes, méthodes, dépendances, commits et PR. Chunker par unité de code ; conserver chemin et hash du commit. Recherche hybride et graphe de dépendances si nécessaire.

      Documentation

      Parser titres, sections, tableaux, versions et dates d’effet. Citer page/section et signaler les documents obsolètes ou contradictoires.

      PDF comptables / tableaux

      Extraction layout-aware et OCR pour scans ; préserver lignes, colonnes, unités et montants. Pour calculer, appeler un outil déterministe, pas le LLM.

      Tickets / incidents

      Index statut, produit, version, date et résolution. Filtrer fraîcheur et statut ; distinguer diagnostic confirmé et hypothèse.

      À retenir
      • Commencer par un seul appel LLM bien contextualisé ; ajouter un agent seulement si un gain est mesuré.
      • Le LLM propose, le backend décide : schémas, permissions et règles métier restent dans le code.
      • Tout borner : étapes, durée, retries, parallélisme et approbation humaine.
      • Tracer chaque appel et rejouer les tests avant tout changement de modèle ou de prompt.
      Étape 4 — orchestration et contrôle

      Le custom harness : le système autour du modèle

      Le LLM n’est pas l’application. Le harness prépare le contexte, choisit le modèle, expose des outils, gère l’état, valide les sorties, applique les permissions et mesure le résultat.

      Règle de sobriété : commencer par un appel LLM bien contextualisé. Ajouter un agent, des boucles ou du multi-agent seulement si un gain mesuré le justifie.

      Quel niveau de harness selon le cas ?

      Votre choix : cliquez sur le niveau qui correspond à votre cas. Il fixe le pattern d’orchestration des réglages avancés.

      1. Q&A simple

      Un appel après retrieval. Pas d’agent. Pour FAQ, procédures et recherche documentaire simple.

      Complexité faible

      2. Router + spécialistes

      Classer l’intention et diriger vers un prompt, un modèle, un RAG ou un outil dédié. Pour assistant multi-domaines.

      Faible à moyenne

      3. Workflow déterministe

      Étapes explicites en code ; LLM utilisé pour extraction, classification ou rédaction. Pour traitement de dossiers récurrents.

      Moyenne

      4. Agent à outils bornés

      Boucle courte, outils typés, état, maximum d’itérations et arrêt explicite. Pour assistant développeur ou recherche multi-sources.

      Moyenne à élevée

      5. Planner / executor / verifier

      Plan, exécution par étape, vérification déterministe et reprise. Pour génération de code et tâches complexes.

      Élevée

      6. Supervisor / multi-agent

      Répartir tâches indépendantes entre spécialistes puis agréger. À réserver aux cas où parallélisme et spécialisation améliorent réellement le résultat.

      Très élevée
      Atelier de paramétrage avancé

      Configurer finement le custom harness

      Le harness est une application métier : ses limites, contrats, permissions et mécanismes de reprise doivent être explicites et testables. Les explications sous chaque réglage précisent ce qu’il contrôle et les risques associés.

      Afficher les 24 réglages du harness — valeurs reprises dans le récapitulatif
      Résilience : timeout par outil, backoff avec jitter, idempotence, circuit breaker, checkpoints, DLQ et compensation des effets partiels. Mesurer le taux de réussite de tâche, les étapes, appels outils, retries, coût, durée, escalades et interventions humaines.

      Pattern recommandé pour le développement logiciel

      Pour dépôts Git, tickets, CI/CD, documentation, Figma ou API internes : tâches bornées, permissions minimales et validation humaine avant toute action irréversible.

      Outils utiles

      • Git : lecture diff, branche isolée, commit et PR.
      • Ticketing : user story, critères d’acceptation.
      • CI : tests, lint, build, SAST, couverture.
      • Docs : standards, ADR et exemples.
      • Observabilité : tokens, appels outils, erreurs, durée.

      Garde-fous

      • Identité de service et permissions par dépôt.
      • Sandbox, allowlist commandes et quotas.
      • Secrets hors prompt et hors logs.
      • Approbation humaine avant merge / déploiement.
      • Diff lisible, tests et provenance du contexte.

      À retenir
      • Optimiser dans l’ordre : sources → retrieval → contexte → routage → serving → vérification.
      • Router : petit modèle pour trier/extraire, grand modèle pour les cas difficiles.
      • Mesurer TTFT, débit, coût par tâche réussie… avant d’ajouter des GPU.
      Étape 5 — optimiser la qualité utile par euro

      Optimiser dans le bon ordre

      Sources & parsing

      Un OCR mauvais, un corpus obsolète ou des ACL erronées contaminent toute la chaîne.

      Retrieval

      Mesurer Recall@K, MRR / nDCG, pertinence ; ajuster chunking, filtres, hybrid search et reranker.

      Prompt & contexte

      Réduire instructions redondantes, résumer historique, dédupliquer passages et limiter le contexte utile.

      Routage modèle

      Petit modèle pour extraction et classification ; grand modèle pour raisonnement, code complexe et cas incertains.

      Serving

      Batching, KV cache, quantification, préchauffage, parallélisme, scheduling GPU et limites de contexte.

      Vérification

      Tests automatiques, revue humaine, analyse des échecs et évaluation continue à chaque changement de modèle ou prompt.

      Routage multi-modèles

      Escalader vers le modèle puissant si…

      • Faible confiance ou preuves contradictoires.
      • Plusieurs documents et contraintes à concilier.
      • Tâche agentique ou code complexe.
      • Échec répété du modèle économique.

      Rester sur le modèle économique si…

      • Classification, tagging, extraction.
      • Réponse claire retrouvée avec preuve.
      • Résumé court et reformulation.
      • Action déterministe déjà spécifiée.

      Étape 7 — workflow de bout en bout

      Les briques à industrialiser autour du RAG et du harness

      Un système LLM en production nécessite un cycle de vie des données, prompts, modèles, évaluations et déploiements. Ces briques évitent que le prototype devienne une chaîne opaque et non maintenable.

      Votre choix : cliquez sur les briques à mettre en place dans votre projet (au moins une).

      1. Connecteurs & data ops

      Connecteurs versionnés, synchronisation incrémentale, détection des changements et suppressions, reprise sur erreur, DLQ, provenance, qualité et classification des données.

      2. Prompt registry

      Prompts versionnés, templates, variables typées, séparation instructions/données, approbation, changelog, tests unitaires et rollback.

      3. Model registry

      Modèle, version, licence, provenance, quantification, contexte, tokenizer, empreinte, compatibilité runtime, évaluation et date de dépréciation.

      4. Evaluation ops

      Golden datasets métier, jeux annotés, tests de régression, tests adversariaux, LLM-as-judge calibré et revue humaine des cas ambigus.

      5. Serving ops

      GPU scheduling, batching, KV cache, quantification, autoscaling, quotas, health checks, files d’attente et isolation des charges.

      6. Observabilité & FinOps

      OpenTelemetry, traces par workflow, tokens, coûts par tâche/équipe/tenant, p50/p95/p99, budgets, alertes, taux d’erreur et capacité GPU.

      7. CI/CD & LLMOps

      Versioning du code, prompts, index et configurations ; quality gates ; canary/blue-green ; rollback ; IaC ; sauvegardes et PRA.

      8. Human-in-the-loop

      Validation des décisions à impact, explication des preuves, approbation d’écriture, gestion des rejets et boucle de feedback exploitable.

      9. Gouvernance

      Propriétaire de chaque corpus, matrice d’accès, rétention, suppression, DPA, sous-traitants, transferts, réversibilité et responsabilités DPO/RSSI.

      Chaîne de livraison recommandée

      Quality gates avant promotion : qualité RAG/harness, sécurité, non-régression, latence, coût, respect des ACL et validation humaine des changements à risque. Un changement de modèle, prompt, parser ou embedding peut modifier le comportement : versionner et retester l’ensemble.

      Étape 8 — exécution

      Feuille de route pragmatique

      Phase 1 — cadrage (1–2 semaines)

      Choisir trois cas mesurables : assistant documentaire, assistant développeur et workflow agentique borné. Définir données, risques, utilisateurs et critères de réussite.

      Phase 2 — prototype (2–4 semaines)

      Proxy LLM, SSO, RAG sur corpus limité, traces et jeu de tests. Comparer API premium et modèle open-weight sur les mêmes tâches.

      Phase 3 — pilote sécurisé (4–6 semaines)

      Brancher ACL, connecteurs, cloisonnement client, tool gateway et validation humaine. Pilote avec groupe représentatif.

      Phase 4 — benchmark (1–2 semaines)

      Mesurer TTFT, tokens/s, concurrence, qualité, coût/tâche, consommation GPU et taux d’échec. Dimensionner ensuite.

      Phase 5 — industrialisation

      HA, sauvegardes, monitoring, alerting, versions, évaluations continues, formation et support.

      Tests minimum avant production

      Qualité

      • Réponse présente / absente du corpus.
      • Documents contradictoires ou obsolètes.
      • Questions multi-sources.
      • Code connu, tests de référence.
      • Outils indisponibles, timeout, arguments incorrects.

      Sécurité

      • Prompt injection dans les sources.
      • Accès croisé entre deux clients.
      • Action sans permission.
      • Secrets dans sources, prompts et sorties.
      • Budget dépassé, arrêt de boucle, reprise.

      Décisions à valider avec la direction

      1. Quels usages sont prioritaires et mesurables ?
      2. Quelles données sont autorisées dans chaque modèle ?
      3. Quel niveau de maîtrise : local, hybride, UE ou global ?
      4. Quel budget pilote et quelle enveloppe récurrente ?
      5. Qui est responsable du produit, du corpus, des accès et de la sécurité ?
      6. Quels seuils qualité / coût / latence déclenchent la production ?

      Glossaire

      ACL
      Liste de contrôle d’accès : qui peut lire quel document ; appliquée côté serveur avant le retrieval.
      Agent
      Composant où un LLM décide d’étapes et appelle des outils ; permissions bornées et critères d’arrêt obligatoires.
      AI Act
      Règlement européen sur l’IA (UE 2024/1689) : obligations graduées selon le risque de l’usage.
      Batching
      Regroupement de requêtes simultanées sur le GPU pour augmenter le débit global.
      BM25
      Algorithme de recherche lexicale par mots-clés ; indispensable pour les identifiants et termes exacts.
      Cache sémantique
      Réutilise une réponse déjà calculée pour une question proche ; évite l’appel au modèle.
      Canary / shadow
      Déploiement progressif sur une petite part du trafic (canary) ou en parallèle sans effet (shadow) pour comparer.
      Chunking
      Découpage des documents en passages indexables ; doit préserver les unités de sens.
      Circuit breaker
      Coupe temporairement les appels vers un service en échec pour éviter l’effet cascade.
      Custom harness
      Couche d’orchestration et de contrôle autour du LLM : prompts, modèles, outils, état, permissions, retries, validations, traces.
      DLQ
      Dead letter queue : file où sont placés les messages en échec permanent pour diagnostic et reprise.
      DPA / SCC
      Accord de traitement des données / clauses contractuelles types encadrant les sous-traitants et transferts hors UE.
      Embedding
      Représentation numérique du sens d’un texte, comparable par similarité.
      FinOps
      Pilotage des coûts : coût par tâche, par équipe, par tenant, budgets et alertes.
      Golden set
      Jeu de questions métier annotées servant de référence pour évaluer et détecter les régressions.
      GPAI
      Modèle d’IA à usage général au sens de l’AI Act ; obligations pour ses fournisseurs depuis août 2025.
      GQA
      Grouped-query attention : technique réduisant la taille du KV cache dans les modèles récents.
      Groundedness
      Degré auquel une réponse est appuyée par les sources fournies.
      Guardrails
      Contrôles automatiques des entrées et sorties : schéma, contenu, sécurité, règles métier.
      HyDE
      Hypothetical document embeddings : générer une réponse hypothétique pour guider la recherche.
      Idempotence
      Propriété d’une action qui produit le même résultat si elle est rejouée ; indispensable avec les retries.
      KV cache
      Mémoire GPU conservant l’état d’attention de chaque session ; croît avec le contexte et la concurrence.
      LLM-as-judge
      Évaluation automatique par un modèle ; à calibrer sur des jugements humains.
      LLMOps
      Cycle de vie industriel des systèmes LLM : versioning, évaluation, déploiement, observabilité.
      MCP
      Model Context Protocol : protocole standard pour exposer outils et données aux modèles.
      Model router
      Composant qui choisit le modèle selon la tâche, le risque, le coût et la latence.
      MRR / nDCG
      Mesures de qualité du classement des résultats de recherche.
      Open-weight
      Modèle dont les poids sont téléchargeables et auto-hébergeables ; licence à vérifier.
      OpenTelemetry
      Standard ouvert de traces, métriques et logs, avec conventions dédiées à l’IA générative.
      OWASP Top 10 LLM
      Référentiel des dix risques de sécurité majeurs des applications LLM (édition 2026).
      Prompt caching
      Mise en cache par le fournisseur des tokens d’entrée répétés (prompt système, documents stables), facturés à prix réduit.
      Prompt injection
      Instructions malveillantes glissées dans une entrée ou un document pour détourner le modèle.
      Quality gate
      Seuil automatique (qualité, sécurité, coût) à franchir avant la mise en production.
      Quantification
      Réduction de la précision des poids (8 ou 4 bits) pour diminuer la mémoire et accélérer l’inférence.
      RAG
      Retrieval augmented generation : recherche de passages pertinents fournis au LLM comme contexte.
      Recall@K
      Part des passages attendus retrouvés parmi les K premiers résultats.
      Recherche hybride
      Combinaison de recherche lexicale (BM25) et vectorielle, fusionnée par exemple avec RRF.
      Reranker
      Modèle qui reclasse les résultats selon leur pertinence réelle à la question.
      RPO / RTO
      Perte de données maximale tolérée / durée maximale d’indisponibilité après incident.
      RRF
      Reciprocal rank fusion : fusion de classements fondée sur les rangs plutôt que sur les scores.
      Saga
      Enchaînement d’étapes multi-systèmes avec actions de compensation en cas d’échec.
      Sandbox
      Environnement isolé (réseau, fichiers, durée) pour exécuter du code ou des outils.
      Serving
      Exécution des modèles en production : runtime, GPU, batching, mise à l’échelle.
      Tenant
      Client ou périmètre isolé dont les données ne doivent jamais se mélanger aux autres.
      Tokens/s
      Vitesse de génération par session ou agrégée sur le serveur.
      TTFT
      Time to first token : délai avant le premier token de la réponse.
      Vector store
      Base qui stocke les embeddings et recherche les plus proches, avec filtres de métadonnées.
